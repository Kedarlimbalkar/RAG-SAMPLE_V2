# Supreme Court of India Legal RAG Pipeline (`Kedarlimbalkar/RAG-SAMPLE_V2`)

A production-grade, 100% custom, self-hosted Legal RAG processing pipeline designed specifically for Supreme Court of India judgments. Built completely from scratch without black-box pre-built parsing APIs or proprietary cloud document tools.

---

## 🏛 Architecture Overview

```
Raw Judgment PDF
       │
       ▼
[Deterministic ID Generation] ──► doc_id = UUIDv5(sha256 of raw PDF bytes)
       │
       ▼
[PyMuPDF Coordinate Parser (scrag/parser.py)]
  ├── Pass 1: Global Coordinate Zoning (Top/Bottom candidate bands across pages)
  │           Dynamic Header/Footer Detection (>=30% page occurrence threshold)
  │
  ├── Pass 2: Page-Level Block Extraction & Zoning
  │     ├── Footnote Separation (bottom band, relative font size < 0.85 * body)
  │     ├── Reading Order Sorting (multi-column detection & vertical flow)
  │     ├── Per-Page Triage (len < 40 chars or garbage ratio > 0.25 -> OCR fallback)
  │     └── Normalization (NFKC, smart quotes, legal de-hyphenation)
  │
  └── Post-Processing: Cross-Page De-hyphenation & Stitched Text Stream
       └── Page Offset Map: page_no -> (start_char, end_char)
       │
       ▼
[PostgreSQL 16 + pgvector + pg_trgm (schema.sql)]
  ├── documents (state machine: pending -> parsed -> chunked -> embedded -> exported)
  ├── pages (coordinates, cleaned text, garbage telemetry, footnotes JSONB)
  ├── metadata (case title, bench, judgment date, citation, trigram indexes)
  ├── parents (~1500 words, 150 overlap, section-aware)
  ├── chunks (~350 words, 50 overlap, linked to parent)
  ├── embeddings (1024-d BGE-M3 dense vectors, HNSW index)
  └── processing_log (audit trail, execution time, retry count)
```

---

## 🔑 Deterministic Identifiers (RFC 4122 UUIDv5)

File paths and arbitrary filenames are never used as primary keys. All entity IDs are derived deterministically:

| Entity | Formula | Example |
|---|---|---|
| **Document** | `UUIDv5(sha256 of raw PDF bytes)` | `a5f22c10-9b88-5182-84b2-297c8ad8901c` |
| **Page** | `f"{doc_id}:{page_no}"` | `a5f22c10-9b88-5182-84b2-297c8ad8901c:1` |
| **Parent Chunk** | `UUIDv5(doc_id + parent_index)` | `d1217e2e-2f9c-50e5-9c5c-7f41e06915f0` |
| **Child Chunk** | `UUIDv5(doc_id + parent_index + child_index)` | `3b59df34-2e21-50e4-9844-0c2d3cf88ce4` |

## 🚀 Quick Start

### 1. Prerequisites
- Docker & Docker Compose
- Python 3.10+ (Recommended Python 3.11+)

### 2. Environment Configuration
```bash
cp .env.example .env
```

### 3. Spin Up PostgreSQL + pgvector
```bash
docker compose up -d
```
This launches PostgreSQL 16 with `pgvector` and `pg_trgm` extensions enabled and automatically executes `schema.sql` on first startup.

### 4. Install Dependencies
```bash
pip install -r requirements.txt
```

### 5. Run Parser Test Suite
```bash
python -m pytest -v tests/test_parser.py
```

## 📦 Database Schema Details (`schema.sql`)

- **`documents`**: Tracks processing lifecycle stages (`pending`, `parsed`, `chunked`, `embedded`, `exported`, `failed`, `quarantined`) with transactional locking via `SELECT ... FOR UPDATE SKIP LOCKED`.
- **`pages`**: Stores page dimensions, raw text, normalized cleaned text, char offset bounds in stitched document, garbage ratio, and structured footnotes.
- **`metadata`**: Case title, case number, bench array, date of judgment, and standard citations with GIN trigram indexes for fuzzy lookup.
- **`parents`**: Coarse-grained semantic context chunks (~1500 words) bound within section boundaries (Facts, Issues, Arguments, Analysis, Order).
- **`chunks`**: Fine-grained child chunks (~350 words) with GIN Full-Text Search index for BM25 hybrid search.
- **`embeddings`**: 1024-dimensional dense vectors generated by local `BAAI/bge-m3` model, indexed with HNSW (`vector_cosine_ops`, `m = 16`, `ef_construction = 64`).
- **`processing_log`**: Comprehensive stage telemetry, execution time in milliseconds, retry logs, and error traces.

---

## 🛠 Parsing & Zoning Engine (`scrag/parser.py`)

- **Two-Pass Zoning**:
  - **Pass 1**: Scans top band ($\le 12\%$ page height) and bottom band ($\ge 88\%$ page height) across all pages. Any line repeating in $\ge 30\%$ of pages is flagged as a dynamic header/footer.
  - **Body Safeguard**: Text outside the top/bottom bands is **NEVER** stripped.
- **Footnote Separation**: Footnotes located at the bottom ($\ge 75\%$ page height) with font size $< 0.85 \times$ median body font size or leading footnote markers are cleanly separated to prevent narrative fragmentation.
- **Reading Order**: Multi-column layouts are automatically detected and sorted by column first, then vertical flow.
- **Text Normalization**: Unicode NFKC normalization, smart quotes/dashes standardized, and legal de-hyphenation preserving compounds like `quasi-judicial` and `sub-section`.
- **Offset Map**: Tracks exact `page_no -> (start_char, end_char)` mapping for downstream chunk attribution.

## ☁️ Google Cloud V2 Storage & CI/CD Pipeline

The project integrates with Google Cloud Platform using **Keyless Authentication (OIDC Workload Identity Federation)**, eliminating static JSON service account keys.

### 1. Dedicated V2 Bucket Partitions (`gs://sc-legal-rag-data-v2`)

| Partition | GCS Path | Purpose |
|---|---|---|
| **Raw PDFs** | `gs://sc-legal-rag-data-v2/raw/` | Inbound Supreme Court judgment PDF documents |
| **Parsed Stream** | `gs://sc-legal-rag-data-v2/parsed-v2/` | Cleaned text streams and page offset maps |
| **Hierarchical Chunks** | `gs://sc-legal-rag-data-v2/chunks-v2/` | Section-aware parent (~1500w) and child (~350w) chunks |
| **Snapshots Archive** | `gs://sc-legal-rag-data-v2/snapshots-v2/` | Snappy-compressed Parquet and JSONL audit snapshots |

### 2. GitHub Actions CI/CD (`.github/workflows/ci-cd.yml`)

The automated workflow executes:
1. **Continuous Integration (CI)**:
   - Triggers on `push` and `pull_request` to `main`.
   - Spins up a Python 3.11 environment.
   - Spins up a live PostgreSQL 16 service container with `pgvector` (`pgvector/pgvector:pg16`).
   - Applies the database DDL from `schema.sql`.
   - Runs the test suite via `pytest tests/`.
2. **Continuous Delivery & Batch Dispatch (CD)**:
   - Uses `google-github-actions/auth@v2` with `id-token: write` permission to exchange GitHub OIDC tokens with GCP Workload Identity Federation.
   - Verifies target bucket connectivity and data partition layouts.
   - Supports manual execution (`workflow_dispatch`) to trigger batch syncs and worker deployments.

### 3. Required GitHub Repository Secrets

Configure the following secrets in **Settings > Secrets and variables > Actions**:
- `GCP_WIF_PROVIDER`: `projects/<PROJECT_NUM>/locations/global/workloadIdentityPools/<POOL>/providers/<PROVIDER>`
- `GCP_WIF_SERVICE_ACCOUNT`: `github-actions-sa@sc-legal-rag-prod.iam.gserviceaccount.com`
